31. Define feature detection and list its major applications in computer vision.

Feature detection is the process of automatically identifying distinctive, repeatable points or regions in an image — called keypoints or interest points — that can be reliably located again in a different image of the same scene, even when the viewpoint, scale, rotation or lighting conditions have changed. Good features occur at places with strong local variation in intensity, such as corners, junctions or textured patches, rather than in flat, uniform regions where every pixel looks the same as its neighbours. Feature detection is the essential first step in almost every higher-level vision task because it reduces an image from millions of raw pixels to a compact, meaningful set of landmarks that downstream algorithms can efficiently compare, match and reason about.

Types of features

  • Edges: boundaries where intensity changes in one direction (Sobel, Canny).
  • Corners: points where intensity changes in two directions; stable and easy to localise (Harris, Shi-Tomasi, FAST).
  • Blobs: regions that differ in brightness from the surroundings (SIFT, SURF, ORB use blob-like keypoints at several scales).

Common detectors

Harris and Shi-Tomasi are classical corner detectors based on the eigenvalues of the gradient covariance matrix. FAST (Features from Accelerated Segment Test) detects corners extremely quickly by comparing a pixel with a circle of 16 neighbours, making it suitable for real-time applications on embedded devices. SIFT and SURF detect keypoints at multiple scales using difference-of-Gaussian or Hessian-based blob detection, giving them scale invariance. ORB combines FAST detection with an orientation assignment and the BRIEF binary descriptor, offering a patent-free, computationally efficient alternative to SIFT that is widely used in mobile and robotics applications.

Applications

  • Image matching and panorama stitching — matched keypoints across overlapping photographs determine the geometric alignment needed to produce seamless wide-angle composites.
  • Object recognition and localisation — a homography computed from feature correspondences can outline a known planar object in a cluttered scene.
  • Object tracking and motion estimation in video — sparse optical flow follows detected keypoints frame to frame, giving velocity and trajectory information.
  • 3D reconstruction, camera calibration and SLAM — triangulating features seen from multiple viewpoints recovers scene geometry, and robots use this continuously to map and navigate unknown environments.
  • Image retrieval and augmented reality — features act as a visual fingerprint, enabling search-by-image engines and letting AR apps anchor virtual content to physical markers.
import cv2
img = cv2.imread("scene.jpg")
gray = cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)              # detectors work on grayscale
orb = cv2.ORB_create(nfeatures=500)                       # create the detector (up to 500 keypoints)
kps = orb.detect(gray, None)                              # list of cv2.KeyPoint (position, size, angle)
out = cv2.drawKeypoints(img, kps, None, color=(0, 255, 0))  # draw the keypoints for viewing
print(len(kps), "keypoints found")

Properties of a good feature

  • Repeatability: found again in another image of the same scene.
  • Distinctiveness: different from other points, so that it can be matched correctly.
  • Invariance: stays stable when the image is rotated, scaled or lit differently.
  • Efficiency: fast to compute and few in number but enough to describe the scene.

Detection in practice

A detector scans the image, gives each pixel a score for how "feature-like" it is, keeps the pixels above a threshold and applies non-maximum suppression so that only the best point in each neighbourhood remains. The result is a few hundred repeatable keypoints instead of millions of pixels, which is what makes matching, tracking and recognition affordable.

32. Explain the difference between feature extraction and feature description, with suitable examples.

Both steps belong to the same pipeline but they answer fundamentally different questions. Feature extraction (often used interchangeably with feature detection) finds and pulls out the informative parts of an image — the keypoints and the pixel patches around them — reducing millions of raw pixels to a few hundred meaningful locations. Its job is spatial: where in the image are the distinctive points? Feature description then converts the neighbourhood of each detected keypoint into a compact numerical vector (the descriptor) that encodes what the local region looks like in a way that is robust to changes in viewpoint, rotation and illumination. Its job is representational: what does each point look like, in a form that can be compared across images? Without extraction there are no points to describe; without description there is no way to tell whether two points in different images correspond to the same physical location.

Example: in a photo of a book cover, FAST marks the corners of letters and the cover (extraction); ORB then records, for each corner, a 256-bit string describing the pixel intensities around it (description). The same book in another photo — even taken from a different angle or under different lighting — produces similar bit strings at the corresponding corners, which are matched by computing the Hamming distance (number of differing bits) and keeping only pairs below a threshold. Some algorithms do both stages: SIFT and ORB provide a detector and a descriptor, and detectAndCompute runs both together for efficiency.

import cv2
gray = cv2.imread("book.jpg", cv2.IMREAD_GRAYSCALE)
orb = cv2.ORB_create()
kps = orb.detect(gray, None)                              # extraction: only keypoint positions
kps, des = orb.compute(gray, kps)                         # description: one 32-byte (256-bit) row per keypoint
print(des.shape)                                          # (number_of_keypoints, 32)
kps2, des2 = orb.detectAndCompute(gray, None)             # both steps in one call

Why they are separated: the same detector can be paired with different descriptors (for example FAST detection with BRIEF description, or FAST with ORB's rotated BRIEF), so the two stages can be chosen independently to balance speed, accuracy and invariance for a given application. A mobile AR app might choose FAST (very fast detection) with a short binary descriptor for real-time performance, while a panorama stitcher might choose SIFT detection with SIFT descriptors for maximum accuracy and scale invariance. The descriptor quality determines how reliably two images can be matched, while the detector quality determines how many stable, repeatable keypoints are available for the descriptor to work with. In OpenCV, algorithms that provide both stages expose a detectAndCompute method that runs them together for efficiency, but the conceptual separation remains.

33. Explain the working principles of Harris and Shi-Tomasi corner detectors and distinguish their outputs.

Both Harris and Shi-Tomasi are based on the same fundamental idea: slide a small window over the image and measure how much the pixel intensities inside the window change when the window is shifted in every direction. At a corner, the intensities change strongly in all directions because the window straddles two or more edges meeting at a point. At an edge, intensities change only perpendicular to the edge but remain constant along it. In a flat, uniform region, there is no significant change in any direction. The magnitude of change is captured mathematically by the structure matrix (also called the auto-correlation or second-moment matrix), which is constructed from the image's horizontal and vertical gradients computed within the window.

Harris corner detector

\[ M=\sum_{w}\begin{bmatrix}I_x^{2}&I_xI_y\\I_xI_y&I_y^{2}\end{bmatrix},\qquad R=\det(M)-k\,\big(\operatorname{trace}(M)\big)^{2} \]

\(I_x,I_y\) are the image gradients in x and y, summed over the window \(w\); \(M\) summarises how strongly the window changes in each direction (its eigenvalues \(\lambda_1,\lambda_2\) are the changes along the two principal directions); \(k\) is a constant, usually 0.04–0.06. Using \(\det M=\lambda_1\lambda_2\) and \(\operatorname{trace}M=\lambda_1+\lambda_2\), the score \(R\) is large and positive for a corner (both \(\lambda\) large), negative for an edge (one large) and small for a flat region. Pixels with \(R\) above a threshold, and which are local maxima, are the corners.

Shi-Tomasi detector

\[ R=\min(\lambda_1,\lambda_2) \]

Shi-Tomasi uses the same matrix \(M\) but scores a point by the smaller eigenvalue; a point is a corner if even the weaker direction changes strongly, i.e. \(\min(\lambda_1,\lambda_2)\) is above a threshold. This avoids the constant \(k\) and gives points that are better for tracking.

import cv2, numpy as np
img = cv2.imread("building.jpg")
gray = cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)

harris = cv2.cornerHarris(np.float32(gray), 2, 3, 0.04)   # blockSize=2 window, Sobel ksize=3, k=0.04 -> response map R
img[harris > 0.01 * harris.max()] = (0, 0, 255)           # mark pixels above 1% of the strongest response in red

pts = cv2.goodFeaturesToTrack(gray, 100, 0.01, 10)        # Shi-Tomasi: max 100 corners, quality 0.01, min distance 10 px
for p in pts.astype(int):                                 # each p is [[x, y]]
    cv2.circle(img, tuple(p[0]), 4, (0, 255, 0), -1)      # draw the corner as a green dot

Practical notes

Both methods work on a grayscale image and rely on intensity gradients, so they are rotation-invariant (rotating the image rotates the gradient directions but does not change the eigenvalues) but not scale-invariant: a sharp corner in a close-up may appear as a smooth edge when the camera zooms out or the image is downsampled. In Harris, the threshold is set relative to the maximum response value, and increasing \(k\) raises the bar for what counts as a corner versus an edge. In Shi-Tomasi, the minDistance parameter enforces a minimum spacing between detected corners, preventing them from clustering on a single texture patch. Because Shi-Tomasi's goodFeaturesToTrack directly returns an ordered array of corner coordinates, its output can be fed immediately into Lucas-Kanade optical-flow tracking without any post-processing.

34. Explain subpixel localization and discuss why it can improve the accuracy of feature-point detection.

Standard feature detectors report corner positions as whole pixel coordinates (integers), but the true geometric corner in the scene almost never falls exactly on a pixel grid point — it may lie anywhere within that pixel's area, meaning the reported position can be off by up to half a pixel in each direction. Subpixel localisation refines this coarse position to a fraction of a pixel (for example (120.3, 87.8) instead of (120, 88)) by analysing the intensity or response values in the immediate neighbourhood of the detected point and interpolating to find the true peak or zero-crossing between the discrete samples. This seemingly small improvement — often reaching an accuracy of 0.05 to 0.1 pixels — has a dramatic impact on tasks where geometry is computed from point positions.

How it works

The corner response near the best pixel is a smooth bump. Fitting a parabola through the response at \(x-1\), \(x\) and \(x+1\) and finding its maximum gives the offset from the central pixel:

\[ \delta=\frac{f(x-1)-f(x+1)}{2\,\big(f(x-1)-2f(x)+f(x+1)\big)} \]

\(f(\cdot)\) is the response (or intensity) value at a pixel, \(x\) is the best integer position and \(\delta\) (between \(-0.5\) and \(+0.5\)) is the shift to add: refined position \(=x+\delta\). With the sample values 6, 9 and 8 in the figure, \(\delta=(6-8)/(2(6-18+8))=0.25\), so the peak lies a quarter of a pixel to the right. The same idea is applied in x and y. OpenCV's cornerSubPix does it iteratively: it looks for the point where the gradient vectors in the neighbourhood are perpendicular to the lines joining them to the point, repeating until the movement is smaller than a set value.

Why it is important

The practical significance of subpixel refinement becomes clear when you consider the downstream computations that depend on point positions. In camera calibration, the intrinsic and extrinsic parameters are solved from a system of equations built around the detected chessboard corners — even a 0.3-pixel systematic bias across a 40-corner board can shift the focal length estimate noticeably and inflate reprojection error. Industrial measurement systems, autonomous vehicle cameras and medical-imaging pipelines all demand calibration accuracy that whole-pixel corners cannot deliver. In stereo vision and 3D reconstruction, depth is triangulated from the horizontal disparity between corresponding points in left and right images — because disparity is itself only a few pixels for distant objects, a half-pixel error in either image can translate to centimetres of depth error at range. Subpixel localisation also underpins optical-flow tracking, panorama stitching and augmented-reality registration, where accumulated positional drift causes visible jitter or seam artefacts over time.

import cv2, numpy as np
gray = cv2.imread("chess.jpg", cv2.IMREAD_GRAYSCALE)
corners = cv2.goodFeaturesToTrack(gray, 50, 0.01, 10)     # integer-accuracy corners, shape (N, 1, 2)
corners = np.float32(corners)                             # cornerSubPix needs float32 points
criteria = (cv2.TERM_CRITERIA_EPS + cv2.TERM_CRITERIA_MAX_ITER, 40, 0.001)   # stop at 40 iterations or move < 0.001 px
refined = cv2.cornerSubPix(gray, corners, (5, 5), (-1, -1), criteria)        # (5,5) = half search window; (-1,-1) = no dead zone
print(corners[0], "->", refined[0])                       # e.g. [120. 88.] -> [120.31 87.82]

Key points to remember

  • Pixel positions are integers; true positions are real numbers; refinement closes the gap using local interpolation of intensity or response values.
  • Method: fit a smooth surface (parabola or second-order Taylor expansion) to the response, or use the gradient-perpendicularity condition in cornerSubPix, iterating until convergence.
  • Typical accuracy of 0.05–0.1 pixel, enough to lower calibration reprojection error from several pixels to a fraction of a pixel.
  • The search window must be large enough to capture the curvature around the peak but small enough to contain only one corner — overlapping windows mix corners and ruin accuracy.

35. Describe the main stages involved in computing feature descriptors and matching features between images.

A descriptor is a compact numerical summary — a fixed-length vector of numbers or bits — that captures the visual appearance of the local region around a keypoint. The fundamental goal is to produce a representation that stays nearly identical when the same physical point is seen under different viewpoints, lighting conditions or scales, while remaining distinct enough that points on different surfaces do not get confused. The entire feature-based pipeline rests on descriptors: without them, a detected keypoint is just coordinates with no identity, making it impossible to tell which point in image A corresponds to which point in image B. Computing descriptors and matching them across images involves several clearly defined stages.

A. Computing a descriptor

  1. Detect keypoints with a detector (Harris, FAST, DoG) and record position, scale and orientation.
  2. Select a local neighbourhood (a patch, e.g. 16×16 pixels in SIFT) whose size follows the keypoint scale.
  3. Normalise the region: rotate it to the keypoint's dominant orientation (rotation invariance) and resize it to a standard size (scale invariance).
  4. Calculate local properties: gradient directions and magnitudes in sub-blocks (SIFT builds histograms of gradient orientation), or intensity comparisons between pixel pairs (BRIEF/ORB).
  5. Generate the descriptor by joining these measurements into one vector (128 numbers for SIFT, 256 bits for ORB).
  6. Normalise the descriptor (for example scale it to unit length) so that changes in brightness and contrast have little effect.

B. Matching between images

  1. Compute descriptors in both images.
  2. For every descriptor of image 1, find the closest descriptors in image 2 using a distance: Euclidean (L2) for float descriptors such as SIFT, Hamming distance (number of differing bits) for binary ones such as ORB.
  3. Keep a match only if it passes a test: cross-check (A's best is B's best too) or Lowe's ratio test, which accepts a match when the best distance is clearly smaller than the second-best (for example best < 0.75 × second).
  4. Use the good matches for homography, stitching or tracking, with RANSAC to remove remaining mistakes.
import cv2
a = cv2.imread("img1.jpg", 0); b = cv2.imread("img2.jpg", 0)    # 0 = load as grayscale
orb = cv2.ORB_create(1000)
ka, da = orb.detectAndCompute(a, None)                    # keypoints + descriptors of image 1
kb, db = orb.detectAndCompute(b, None)                    # keypoints + descriptors of image 2
bf = cv2.BFMatcher(cv2.NORM_HAMMING, crossCheck=True)     # brute force; Hamming because ORB is binary
matches = sorted(bf.match(da, db), key=lambda m: m.distance)   # smaller distance = better match
vis = cv2.drawMatches(a, ka, b, kb, matches[:30], None)   # draw the 30 best matches

Choosing the descriptor is a trade-off between accuracy and speed. SIFT produces 128-dimensional float vectors with strong invariance to scale, rotation and moderate viewpoint changes, but each descriptor comparison requires 128 floating-point subtractions and a square-root, making brute-force matching expensive for large sets. ORB encodes 256-bit binary strings computed from simple pixel-pair intensity comparisons, so matching uses XOR-and-popcount (Hamming distance), which modern CPUs execute in a single instruction — this makes ORB orders of magnitude faster than SIFT and well-suited for real-time applications like mobile AR and SLAM. SURF sits between the two in both accuracy and speed. The matching distance must always match the descriptor type: L2 norm for float descriptors, Hamming for binary ones — using the wrong metric silently produces garbage matches.

36. Apply FLANN-based feature matching to identify corresponding keypoints in two images. Explain the major steps.

FLANN (Fast Library for Approximate Nearest Neighbours) is a library specifically designed for high-dimensional nearest-neighbour search, which is the core operation in descriptor matching. When two images together produce thousands of keypoints, brute-force matching must compare every query descriptor against every database descriptor — an \(O(N\times M)\) operation that becomes prohibitively slow for real-time applications or large image databases. FLANN avoids this cost by first building a spatial search structure (an index) over the database descriptors and then searching it approximately, accepting a tiny probability of missing the exact best match in exchange for a speed-up that can reach 10–100× depending on the number of descriptors and the dimensionality of the feature space.

Major steps

  1. Detect keypoints and compute descriptors in the query and train images (SIFT or ORB).
  2. Choose the index to suit the descriptor: randomised KD-trees for float descriptors (SIFT/SURF), which partition the 128-dimensional space into regions for fast lookup; LSH (locality-sensitive hashing) for binary descriptors (ORB), which groups similar bit strings into the same hash buckets.
  3. Create the matcher with index parameters (number of trees for KD-tree, or number of hash tables and key size for LSH) and search parameters (number of checks — the number of leaf nodes examined per query; more checks give higher recall but increase latency proportionally).
  4. Find the two nearest neighbours of each query descriptor with knnMatch(k=2).
  5. Apply Lowe's ratio test: keep a match if \(d_1<0.7\,d_2\), where \(d_1\) and \(d_2\) are the distances to the best and second-best neighbours; an ambiguous match has \(d_1\approx d_2\) and is rejected.
  6. Use or draw the good matches (drawMatches), then estimate a homography with RANSAC if the object is to be located.
import cv2
q = cv2.imread("query.jpg", 0); t = cv2.imread("scene.jpg", 0)
sift = cv2.SIFT_create()                                  # float descriptors (128-D)
kq, dq = sift.detectAndCompute(q, None)
kt, dt = sift.detectAndCompute(t, None)

index_params = dict(algorithm=1, trees=5)                 # algorithm 1 = KD-tree, 5 trees
search_params = dict(checks=50)                           # leaves visited per search; higher = more exact
flann = cv2.FlannBasedMatcher(index_params, search_params)
pairs = flann.knnMatch(dq, dt, k=2)                       # two nearest neighbours for every query descriptor

good = [m for m, n in pairs if m.distance < 0.7 * n.distance]   # ratio test keeps only unambiguous matches
vis = cv2.drawMatches(q, kq, t, kt, good, None)
# for ORB use: dict(algorithm=6, table_number=6, key_size=12, multi_probe_level=1)  # 6 = LSH

Remember: KD-tree for SIFT (floats), LSH for ORB (bits); the ratio test is what removes false matches.

Brute force or FLANN? The brute-force matcher compares every pair of descriptors and guarantees the exact nearest neighbour; it is perfectly adequate and often faster for a few hundred keypoints because it has no indexing overhead. FLANN pays an upfront cost to build its KD-tree or LSH index, but that investment is repaid many times over when the descriptor count reaches the thousands — panorama stitching with SIFT on high-resolution images, for example, can easily produce 5,000+ descriptors per image. Matching quality is controlled by two knobs: the index structure parameters (number of trees for KD-tree, or table count for LSH) and the ratio-test threshold — a stricter ratio like 0.6 yields fewer but highly reliable matches, while a relaxed 0.8 returns more correspondences at the cost of more false positives that RANSAC must later clean up.

Output: a list of good matches — pairs of keypoint indices, one from each image — that can be visualised as lines between the two images using drawMatches or fed directly to findHomography with RANSAC to compute the geometric transformation relating the two views.

37. Apply homography estimation to localize a planar object in an image and explain the role of matched keypoints and outlier rejection.

A homography is a \(3\times3\) projective transformation matrix \(H\) that maps every point on one plane to the corresponding point on another plane as seen through a camera. The key geometric insight is that when the scene surface is planar — a book cover, a poster, a road sign, a warehouse box face — the relationship between any two views of that surface is completely described by a single homography, regardless of how different the camera angles are. This makes homography estimation one of the most practical tools in computer vision: by computing \(H\) from detected feature correspondences between a known reference image of the object and a live scene, we can localise the object precisely even under significant rotation, scaling, foreshortening or perspective distortion.

\[ s\begin{bmatrix}x'\\y'\\1\end{bmatrix}=\begin{bmatrix}h_{11}&h_{12}&h_{13}\\h_{21}&h_{22}&h_{23}\\h_{31}&h_{32}&1\end{bmatrix}\begin{bmatrix}x\\y\\1\end{bmatrix} \]

\((x,y)\) is a point in the reference image, \((x',y')\) the corresponding point in the scene, \(s\) is a scale factor (divide by it to get the pixel position) and the nine entries of \(H\) hold rotation, translation, scaling and perspective. Fixing the last entry to 1 leaves 8 unknowns, and each point pair gives 2 equations, so at least 4 matched points are needed.

Steps

  1. Detect keypoints and compute descriptors in the reference image and in the scene.
  2. Match them (FLANN or brute force) and keep the good matches with the ratio test.
  3. Estimate \(H\) from the matched points: findHomography.
  4. Reject outliers with RANSAC: repeatedly pick 4 random matches, compute \(H\), count how many other matches agree within a pixel threshold (the inliers) and keep the \(H\) with most inliers. Wrong matches (the red outlier in the figure) do not fit the plane and are discarded.
  5. Transform the object corners with perspectiveTransform and draw the resulting quadrilateral in the scene.

The matched keypoints supply the correspondences without which \(H\) cannot be computed; outlier rejection is essential because even a few wrong matches would give a badly wrong \(H\).

import cv2, numpy as np
# kq, kt = keypoints of query / scene; good = matches that passed the ratio test (see Q36)
src = np.float32([kq[m.queryIdx].pt for m in good]).reshape(-1, 1, 2)   # points in the query image
dst = np.float32([kt[m.trainIdx].pt for m in good]).reshape(-1, 1, 2)   # same points in the scene
H, mask = cv2.findHomography(src, dst, cv2.RANSAC, 5.0)   # 5.0 px = max error to count as an inlier; mask marks inliers
h, w = q.shape                                            # size of the reference image
corners = np.float32([[0, 0], [w, 0], [w, h], [0, h]]).reshape(-1, 1, 2)
box = cv2.perspectiveTransform(corners, H)                # where the 4 corners land in the scene
cv2.polylines(scene, [np.int32(box)], True, (0, 255, 0), 3)   # outline the located object

Limits of the method

A homography is valid only for a flat surface or a pure camera rotation (where every depth behaves as one plane at infinity); for a genuinely 3D object with multiple surfaces at different depths, no single \(H\) can fit all points simultaneously — you would need the fundamental matrix or a full 3D model instead. The estimation also requires at least 4 non-collinear inlier matches and sufficient texture on the object to generate reliable descriptors; textureless or highly repetitive surfaces (a white wall, a brick pattern) either produce too few keypoints or too many ambiguous matches. Always check the inlier count (mask.sum()) before trusting the result — a low ratio of inliers to total matches is a strong signal that the object was not found. The RANSAC reprojection threshold (typically 3–5 pixels) controls how tightly a match must agree with the model to count as an inlier; too tight rejects correct matches under noise, too loose admits outliers that distort \(H\).

38. Apply a perspective transformation to convert a distorted view of a planar object into a frontal view.

When a flat object — a document, whiteboard, number plate or book page — is photographed from an oblique angle rather than head-on, the resulting image exhibits perspective distortion: parallel edges converge, the shape appears trapezoidal and the near side looks proportionally larger than the far side. Perspective correction (also called rectification or "de-warping") computes a projective transformation that reverses this distortion, re-projecting the object as if the camera had been positioned exactly perpendicular to the surface. The corrected output is a clean, rectangular frontal view suitable for OCR, measurement, archival scanning or further image analysis. This is one of the most commonly used geometric transformations in practical computer vision, powering document-scanner apps, automatic whiteboard capture, overhead lane-detection views in autonomous driving and art restoration photography.

The mapping is a homography (Q37). For a destination pixel the position in the source is found with

\[ x'=\frac{h_{11}x+h_{12}y+h_{13}}{h_{31}x+h_{32}y+1},\qquad y'=\frac{h_{21}x+h_{22}y+h_{23}}{h_{31}x+h_{32}y+1} \]

\((x,y)\) is a point in the skewed image, \((x',y')\) its position in the corrected image and \(h_{ij}\) are the entries of the \(3\times3\) matrix. The division by the denominator is what makes parallel lines converge (perspective), and an affine transformation is the special case \(h_{31}=h_{32}=0\), which cannot do this. Four point pairs determine the eight unknown \(h\) values.

Steps

  1. Locate the four corners of the object in the input (by clicking, or by contour detection and approxPolyDP).
  2. Choose where these four corners should go: the corners of a rectangle of the wanted output size.
  3. Compute the matrix with getPerspectiveTransform.
  4. Apply it with warpPerspective and show or save the result.
import cv2, numpy as np
img = cv2.imread("skewed_page.jpg")
src = np.float32([[120, 80], [520, 60], [560, 400], [90, 430]])   # 4 corners in the photo: TL, TR, BR, BL (same order as dst!)
W, H = 400, 500                                           # size of the frontal output
dst = np.float32([[0, 0], [W, 0], [W, H], [0, H]])        # where those corners should land
M = cv2.getPerspectiveTransform(src, dst)                 # exact 3x3 matrix from 4 point pairs
flat = cv2.warpPerspective(img, M, (W, H))                # apply: output size is (width, height)
cv2.imwrite("frontal.jpg", flat)

Note: getPerspectiveTransform uses exactly 4 points; with many noisy matches use findHomography instead. Points must be listed in the same order in src and dst.

Practical uses and cautions

Perspective correction is central to mobile document scanning (apps like CamScanner detect the page quadrilateral automatically, warp it and produce a clean PDF), whiteboard-to-notes conversion, licence-plate recognition in traffic systems (where the plate is almost never perfectly frontal) and bird's-eye view generation for autonomous driving lane detection. Accuracy depends critically on the four source corner points — a one-pixel error at a corner can shift a distant part of the corrected image by several pixels, so subpixel refinement or careful manual placement matters. The output dimensions should preserve the real aspect ratio of the object; guessing a square output for a rectangular document will stretch the text. This method works only for planar surfaces — a curved book spine or a cylindrical can cannot be corrected by a single homography. For the interpolation flag in warpPerspective, INTER_LINEAR is the default and is fast, while INTER_CUBIC gives smoother results at a small extra cost, and both are preferred over nearest-neighbour which introduces visible staircase artefacts on text and edges.

39. Analyze the working of cascade classifiers and discuss how scale, illumination, and pose variations affect their detection performance.

A cascade classifier, introduced by Viola and Jones in 2001 for real-time face detection, detects objects by sliding a fixed-size window across the image and passing each window position through a series of increasingly strict tests. The framework rests on three mutually reinforcing ideas. Haar-like features encode local contrast patterns — for instance the difference between the sum of pixels in a bright rectangular region and the sum in an adjacent dark region captures the fact that the eye sockets are darker than the cheek or forehead. The integral image (also called a summed-area table) pre-computes cumulative pixel sums so that the sum of any axis-aligned rectangle can be evaluated with exactly four array look-ups regardless of its size, making Haar feature evaluation essentially free. AdaBoost (Adaptive Boosting) then selects the most discriminative features from the enormous pool of all possible rectangle placements and combines hundreds of individually weak classifiers into a strong composite classifier that achieves high accuracy.

Working

The strong classifiers are arranged in a cascade of stages, as in the figure. Early stages use a handful of features and reject most background windows cheaply; only windows that look like the object continue to the more detailed later stages. A window is reported as an object only if it passes all stages. To find objects of different sizes, the detector is run on an image pyramid (or with a growing window), and overlapping detections are merged using a minimum-neighbours rule.

Summary: cascade classifiers remain valuable for constrained real-time detection scenarios — frontal face detection under reasonable lighting is the classic success case, running at 15–30 fps even on modest hardware because the cascade rejects over 99% of windows in the first two stages. However, they are fundamentally limited by their reliance on a single viewpoint and fixed feature templates: strong pose variation, dramatic lighting shifts, heavy occlusion and non-rigid deformation all degrade performance significantly. For unconstrained detection across poses and conditions, deep-learning detectors like YOLO and SSD have largely superseded cascades, though the Viola-Jones framework remains an important conceptual foundation and a practical choice when computational resources are extremely limited or training data is scarce.

40. Evaluate the effectiveness of feature matching and video analysis for real-time object recognition, considering reliability and processing speed.

Feature matching recognises a known object in a new image by detecting keypoints, computing descriptors and finding correspondences with a stored reference — essentially answering "is the same physical pattern present here?" Video analysis extends this to the temporal domain: rather than running the full detect-describe-match pipeline on every frame independently, the system tracks already-found keypoints from one frame to the next using lightweight methods like sparse optical flow, re-running the expensive matching step only when tracking confidence drops or when a new object must be identified. Whether this combination is effective for real-time recognition depends on two competing requirements: reliability (correct detection under viewpoint, lighting and motion changes) and processing speed (fitting the full pipeline within a per-frame time budget).

Reliability

  • Strengths: scale- and rotation-invariant descriptors (SIFT, ORB) cope with viewpoint changes, partial occlusion (only some keypoints are needed) and clutter; RANSAC removes false matches; no large training set is needed, a single reference image is enough.
  • Weaknesses: fails on texture-less or shiny objects (few keypoints), motion blur, strong lighting change or very large viewpoint change; works best on rigid, planar, textured objects; many similar patterns cause wrong matches.

A frame budget of about 33 ms is available at 30 frames per second, so the full pipeline must fit in it. Practical ways to meet it: use ORB; reduce resolution; detect only inside the region of interest; run the full detection and matching only every N frames or when tracking is lost, and between them use cheap tracking such as Lucas-Kanade optical flow; use a GPU where available.

Evaluation: feature matching with tracking is effective for real-time recognition of textured, rigid objects (posters, book covers, markers, landmarks) with ORB, giving a good balance of speed and reliability; it is not suitable for texture-less, deformable or highly varying object classes, where a learned detector (CNN, YOLO) is preferred.
